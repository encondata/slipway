# Phase 3 design: Environments and slots

Branch `sirdar` at 83dca5d. This is the design for phase 3 of bringing Sirdar into Slipway: environments, Blue/Green slots on SSH hosts with a separate data server, Switchyard as the traffic switch, Activate and switch back, and Cloudflare DNS. It builds on phase 1 (manifest and steps) and phase 2 (data safety, Slipway's `docs/phase2-data-safety.md`, "P2" below). Phase 2's real-host checks (sirdar-integration.md, "Real-host checks") should pass before phase 3 merges, because every phase 3 data path runs phase 2's steps on another host.

Line references are to Slipway at 83dca5d unless another file is named. `SS/` is BaseCampV3 on branch `slipway-manifest`. Nothing in Slipway is written for ServerSherpa: the data server, the attached-data keys and the health paths are declared in the app's own slipway.yml (§5). An instance that is not in an environment deploys, backs up, restores and publishes exactly as today (I1).

Settled before this design and taken as given: no Sirdar environment survives and nothing is imported; Nginx Proxy Manager is gone and Switchyard is the only LAN proxy; no portal sign-in; one engine (Slipway's shell steps, no Ansible); Terraform stays for Proxmox and pyvmomi for ESXi (phase 5).

This revision answers a 26-point review of the first draft; Appendix A restates each point, says where the spec now handles it, and gives the reason for each point not taken (in full or in part).

## 0. Decisions and why

| # | Decision | Why |
|---|---|---|
| D1 | An **environment** is a new row (`environments`). Its **slots** are ordinary `Instance` rows with `environment_id` and `slot` (`blue`, `green`, or `data` for the data server). There is no slot table. | Every per-instance mechanism (folders, releases, ports, host lock, logs, steps, retry, recovery) keeps working per slot without change (slipway-now §13). Slot slugs `<env>-blue`, `<env>-green`, `<env>-data` keep ServerSherpa's `STACK_ENV={slipway.slug}` projects and volumes distinct even when two slots share a host, so `_check_projects_free` (deployer.py:4573) keeps passing. |
| D2 | Two data modes: `slot` (one app slot that holds its own data, exactly as a phase 2 instance) and `server` (a separate **data server** instance runs the app's own data services; one or two app slots attach to it). Two app slots need `server`. Phase 4 adds `managed`. | Blue/Green needs data both slots can reach. Sirdar's LAN Blue/Green is the same shape with VMs (sirdar-envs-slots §0, §3); phase 3 uses existing SSH hosts. A single-slot `slot` environment gives every app the environment pages, Activate and DNS without a second host. |
| D3 | The **data owner** of an environment is the data server (mode `server`) or the only app slot (mode `slot`). Every phase 2 data field (backups, `keep_backups`, `seed_snapshot_id`, `seed_content`, `content_pending`, `live_identity`, `identity_*`, `data_dirty`, `fresh_data`, `last_control_at`) and the `FirstAdmin` row live on the data owner instance. App slots in mode `server` leave those columns at their defaults and nothing reads or writes them: every phase 2 write of one of these fields goes through `environments.owner_of(instance)` (§7.5 has the table). The owner never changes for the life of the environment; in every mode but `slot` it is the `slot = data` instance (phase 4's `managed` mode included, §14). | No phase 2 table changes shape: `Backup.instance_id`, `FirstAdmin.instance_id` and the dirty state stay per instance. In mode `slot` the owner is the slot itself, so phase 2 behaviour is unchanged there by construction. An owner that moved with Activate would split backups, the first admin and the dirty state across slots. |
| D4 | The data commands (`has_data`, `data_up`, `dump`, `verify_dump`, `revision`, `restore`, `export_files`, `import_files`, `after_import`) run **on the data owner's host**, with the data owner's live release. Backups are files in the data owner's `backups/` folder. Only `accepts` (needs the slot's code), `first_admin` and `seed` (need the running app) run on an app slot. | Backups then don't depend on which slot is active and survive a slot's removal (Sirdar keeps them on whichever slot ran the dump: sirdar-envs-slots §7, §13). On the data server the database and object store are local, so ServerSherpa's `pgdump`, `restore`, `export-objects` and `import-objects` work without the `STACK_OBJECTS_ENDPOINT` change the research proposed (sirdar-data-server §5). |
| D5 | **Settings, services, variables and secrets belong to the environment** (`environments.app_settings`, `app_services`, `env`, `app_secrets`). Secrets are generated **when the environment is created**, from slipway.yml at the branch head. A secret that a later slipway.yml adds is generated by the first job that needs it and saved on the environment with a compare-and-set on `environments.secrets_version`. Slots' own columns stay empty. | Two slots on one database must share `POSTGRES_PASSWORD`, the pepper and the TOTP key, and sessions must survive a switch (sirdar-envs-slots §6). Generating at create, as Sirdar does, removes the race between two slots' first deploys (slipway-now §14.2). A version column, not the ciphertext, is compared, because Fernet encrypts the same value differently each time (core/crypto.py:83-90). |
| D6 | slipway.yml gains generic keys (§5): `services.<name>.health`, `data.migrations`, `data.attach` (the `.env` keys that point an app slot at data elsewhere, from named endpoints) and `data.server` (how the app's own data services run alone on a host). | The data server's `.env` keys, which service stays on the data server, and the health paths are ServerSherpa knowledge Sirdar hard-coded (`lan_slots.py:102-129`, `envfile.py:140-191`, `smoke.py:24`). The manifest declares them; the same `data.attach` serves phase 4's managed Postgres and Spaces. |
| D7 | **Two app slots require `data.migrations: expand_contract`.** Environment create and Add slot refuse without it. The contract holds between adjacent releases only, so a deploy to the idle slot is refused while the **active** release is already behind the schema (its `accepts` answers 3 on the current revision, which happens after a switch back), unless the person confirms the new release removes nothing the active one uses (§7.6). | The idle slot's `start` migrates the shared database while the live slot keeps serving old code (sirdar-data-server §4). Slipway can't check that a migration is backward-compatible; Sirdar only wrote it in a dialog. Requiring the app to declare it makes the contract explicit. After a switch back, blue (N) serves a database green (N+1) migrated; a contract step in N+2 could drop what N still reads. |
| D8 | **One job at a time per environment, with one exception: Activate may run beside a job that only reads the data.** Every environment job holds two runner keys, `(env, traffic)` and `(env, data)`, except `activate` (traffic only) and the owner's `backup` and `snapshot` without `stop_app` (data only). Standalone instances keep one key, their id. A partial unique index on `deployments.environment_id` over every kind but `activate`, and another over `activate` alone, back it up. | Sirdar has one running deployment per environment. Activate during a slot deploy, a restore while a slot starts, and two slots generating secrets are all excluded by the two-key rule. Switch back after a bad activation must not wait behind a long Back up now or snapshot export, which touch neither slot nor Switchyard. |
| D9 | Environment-wide jobs are `Deployment` rows with `environment_id` set and `instance_id` NULL: `activate`, `publish`, `discard`, `remove_slot`, `teardown`. Jobs on a slot or the data server are ordinary instance jobs with `environment_id` also set. | Steps, LogSink, retry and the Deployments list are keyed on Deployment (D1 of P2). Removing a slot or the environment deletes instance rows, whose deployments cascade; an environment-level row survives and keeps the log. |
| D10 | Environments are **never hard-deleted**. Delete sets `status = deleted` and `deleted_at`; the name is unique among live environments only. | The teardown job, its log and the audit trail stay readable after a delete. `resources.environment_id` is `ON DELETE RESTRICT` (phase 4 safety, sirdar-digitalocean §5) and soft deletion keeps it simple. |
| D11 | An Update always goes to the **idle** slot. It goes live by itself (a chained `activate` job) only when nothing is live, or `auto_activate` is on. With a single app slot, a deploy updates it in place and its traffic follows (no switch). | Sirdar's `target_slot` and `goes_live` (sirdar-envs-slots §3). |
| D12 | **Chains are hooks, not a scheduler.** When an environment job succeeds while Slipway is running normally, `environments.after_job` queues the next one by fixed rules: data server's first deploy → the first slot's deploy; a slot deploy with `options.go_live` → `activate`; a snapshot with `options.then = "teardown"` → `teardown`. A refused follow-up, a job that succeeded while Slipway was shutting down, and a job that recovery marked succeeded after a restart leave `environments.notice` with the button that starts the next job by hand. | Each job keeps its own log, retry and permissions; a failure stops the chain and Retry continues it, because the hook runs on every success. A job that succeeded has no Retry, so a chain that stopped on a success must say so. |
| D13 | **Activate** is `check, [start_slot], smoke, [dns], switch, [seed]`. The one `switch` step plans, applies in one batch and one Switchyard apply, checks the names through Switchyard (its verify phase) and, on any failure, cancel or shutdown, puts back what it recorded. `environments.active_slot_id` changes only after the verify phase passes. **Switch back** is Activate of the other slot. | Sirdar's `lan_switch` (sirdar-traffic §6-7) with Switchyard's stage-then-apply. The old slot keeps running, so going back is a switch, not a rebuild (Sirdar: "go back = activate the other slot"). One step keeps the put-back record in memory where it is used; DNS goes first because Caddy can't get a certificate for a name with no record (Sirdar also publishes DNS before its slot smoke and switch, `steps.py:_bg_plan`). |
| D14 | One **TrafficBackend** interface; phase 3 builds `switchyard` (repoint proxy hosts); `do_lb` is reserved and its contract fixed for phase 4. **DNS publishing** (records at a fixed address, through Cloudflare) is a separate step. There is no DNS-switching backend. | On the LAN, DNS doesn't move on a switch (records point at the WAN address; sirdar-traffic §2). Switching by DNS can't be checked through the real path, can't be put back for clients that cached the old answer, and needs slots that terminate TLS themselves, which ServerSherpa's LAN slots don't (Caddy runs only with `STACK_CADDY=1`). |
| D15 | Every Switchyard host and DNS record an environment manages is a **`resources`** row (provider, kind, provider id, origin `created`/`claimed`), written in its own transaction the moment the provider answers. Slipway changes or deletes only recorded objects that still carry its marker; anything else is a blocker, stopping the step before any change. | Sirdar's `managed_records`/`do_resources` rules (sirdar-traffic §3). External ids are reused (Switchyard's are small integers), so every write re-reads the object first. The same table holds phase 4's droplets, databases, buckets and load balancers. |
| D16 | **Data jobs on a shared database stop every app slot** (`stop_slots`) before they replace data, and afterwards, **before the owner's `finish`**, start the **lead** slot with its live `start` (it migrates forward). The lead slot is the active one, or, with nothing active, the app slot whose deploy finished last. The other slot is started again only when it runs the same commit and the identity keys didn't change; otherwise it stays stopped and is marked **stale** (Activate refuses it until it is deployed again). A lead slot that fails to start fails the job and leaves the owner held. | Restoring under a running writer corrupts the copy, and `ss-stack restore` stops writers on its own host only (`ss-stack:469-472`). The idle slot may run newer code than the restored schema accepts; a stale mark is honest and cheap. Everything after `finish` counts as live and ends the job as succeeded (`_end_after_live`, deployer.py:4834), so starting the slots there would turn "both slots down" into a success. |
| D17 | A failed deploy to the idle slot is settled by **Discard <green>** (kind `discard`): green is stopped and marked stale, the active slot is checked on the current database, and the owner's dirty state clears. Nothing is restored. **Roll back** stays as a second action that needs `data:reset` as well as `data:restore`; it restores the pre-deploy backup and says that writes made through the active slot since then are lost. Roll back after a **successful** activation is not offered: the way back is Switch back (code only), or Restore that backup by hand. | The active slot kept serving through the failed deploy, so restoring the pre-deploy backup throws away what users wrote since. ServerSherpa's Alembic runs every migration of an upgrade in one transaction (`api/migrations/env.py:29,40`), so a failed migration leaves the database at the revision the active slot runs; a migration that succeeded is one the active slot accepts by the expand/contract rule. |
| D18 | The data server's `.env` holds only `data.server.secrets`; every other secret line is written **empty**. ServerSherpa's `ss-stack` then runs only its db and storage stacks on that host (S7), since the app stacks' compose files refuse an empty `SS_JWT_SECRET` (`${…:?}`, api/compose.yml:23-25,45). The data owner's **identity values** come from the environment's secrets and variables, never from the server's `.env`. Its client list (`{server.clients}`) is the app slots' hosts' `lan_address` (or `upstream_address`), which must be IP literals; a data server on an app slot's host is refused. It is updated on its own ("Update the data server"), never as part of a slot deploy. | Sirdar's data VM got only `POSTGRES_PASSWORD` and `SPACES_SECRET_KEY` (sirdar-data-server §2). ServerSherpa's `pg_hba` takes IPv4 addresses only (`ss-stack:131-177`), and a connection from a container on the same host arrives from a Docker bridge address, never the host's LAN address. Sirdar re-applied the data VM on every update and restarted the live slot's database without warning (sirdar-data-server §3); Slipway makes it a deliberate step and checks the live slot afterwards. |
| D19 | No host firewall management in phase 3. The data server's access control is the app's own (`pg_hba` from `{server.clients}`, the object store's key). The environment page says the data server's published ports are reachable from the whole LAN; docs/environments.md shows the `DOCKER-USER` rules to add by hand and ServerSherpa's `STACK_BIND_IP`. | Sirdar's `DOCKER-USER` chains need root and a systemd unit; Slipway's hosts may run as a docker-group user or on Unraid. Open question 1. |
| D20 | New permissions (integration doc decision 4): `environments:read`, `environments:write`, `environments:delete`, `traffic:switch`. Restoring data reuses phase 2's `data:restore` and `data:reset`. Actions that replace or remove data, remove a slot or delete the environment need the **environment's** name typed back. | Decision 4. A phase 2 data endpoint called on the data owner compares `confirm` with the environment's name, so people type the name they see. |
| D21 | `hosts.environment` is renamed **`label`** (API keeps `environment` as an input alias and output copy for one release). Hosts gain `provider` (`ssh` by default), `provider_id`, `lan_address` and `owner_environment_id`. | The free-text label clashes with the new model (slipway-now §2). Phases 4-5 make hosts with a provider and an owning environment. `lan_address` is the address other hosts' connections arrive from, when it isn't the proxy address (a multi-homed host). |
| D22 | Slots never publish their own routes: `deployer.has_routes` is false for environment members, and the environment's names are published only by the traffic code, under an **environment** marker in Switchyard. | Two slots carrying the same hostname would otherwise hit Switchyard's ownership conflict (slipway-now §5), or an idle slot would steal traffic. |
| D23 | Smoke tests run on the slot's host over its SSH session (`curl` to the published port with `Host` set), then, after the switch, from the Slipway server through Switchyard's **traffic address** with SNI. Paths come from `services.<name>.health` (default `/`); 200-399 passes. | Sirdar's slot and public smoke tests (sirdar-traffic §6). The paths move to the manifest (Sirdar's table lacks `learn`). |
| D24 | **Names that don't move go out first.** The data server's deploy publishes the environment's DNS records (fixed address) and creates its server-following Switchyard hosts as soon as it is live, without waiting for Activate. Starter content (`seed`) of a new environment runs in its first Activate, after the switch, on the slot that just went live. | ServerSherpa's `seed-label-fonts` uploads through `https://spaces.<domain>`, which containers reach through Switchyard (`labels/font_seed.py:33`, api/compose.yml:28,70): before the first switch there is no route (mode `slot`) or no certificate (no DNS record yet) for it. Server-following hosts never move between slots, so creating them early changes no traffic. |

## 1. Invariants

- **I1. Nothing changes for instances outside environments.** Their step lists, `.env` bytes, proxy sync (markers, calls), data jobs, permissions and pages are exactly phase 2's. Golden tests compare them (test 44).
- **I2. One job per environment, except Activate beside a read-only data job.** No two queued or running jobs of an environment share a runner key (D8): at most one non-`activate` job and at most one `activate`, and an `activate` runs only beside the owner's `backup` or a `snapshot` without `stop_app` (runner keys, `queue_job` check, the two partial unique indexes).
- **I3. Shared secrets and identity are the environment's.** An environment's secrets are generated at create (or by the first job that needs a new one) and saved only on the environment, by compare-and-set on `secrets_version`. No slot generates its own. Every identity value Slipway records (`live_identity`, `Backup.identity`, a snapshot's identity) is the environment's, whichever member's `.env` the job wrote.
- **I4. Data jobs run where the data is.** Every data command except `accepts`, `first_admin` and `seed` runs on the data owner's host; backups live there.
- **I5. Refuse before changing.** Every flow (§9) lists its refusals; each is checked before the first change (a Switchyard PUT, a DNS write, a container stop, a volume removal, a `start`). A switch whose plan has a blocker changes nothing.
- **I6. Traffic moves only after a check.** Active-following hosts are pointed at a slot only by Activate's `switch` step, after `smoke`; `active_slot_id` is written only after its verify phase passes. Any failure after the first traffic write puts back what was recorded; a put-back that can't finish leaves an **unresolved switch** that fences off slot rebuilds and every sync of active-following hosts until it is resolved. A sync (after an in-place deploy or a data server deploy) never repoints an active-following host to another slot.
- **I7. Only what Slipway recorded.** Slipway updates or deletes a Switchyard host or DNS record only when a `resources` row names it **and** the live object still carries Slipway's marker for this environment (or is a claimed record, which is updated and never deleted).
- **I8. A shared database is never changed under a running app.** Restore, roll back, reset and Start over stop every app slot first (D16); deploys change it only through the idle slot's `start` (expand/contract, D7) or the data server's own `start`.
- **I9. A job that leaves an app slot down doesn't succeed.** A data job on a shared database succeeds only once its lead slot has started (D16); a failure there fails the job and holds the owner.

## 2. Concepts

| Term | Meaning |
|---|---|
| Environment | One app from one repository, branch and manifest path: settings, secrets, names, slots, traffic. Name `^[a-z][a-z0-9-]{0,24}[a-z0-9]$` (2-26), unique among live environments. 26 leaves room for `-green` within the 32 characters an app's own names often allow (ServerSherpa's `STACK_ENV`, `ss-stack:78-80`) and within the instance slug's 63. |
| App slot | An instance with `slot` `blue` or `green`. Runs the whole app (mode `slot`) or the app without its data services (mode `server`). |
| Data server | An instance with `slot = data`, on a host that no app slot of the environment uses. Runs the manifest's data services only. |
| Data owner | The data server (mode `server`) or the only app slot (mode `slot`). Holds every phase 2 data field (D3). |
| Active slot | `environments.active_slot_id`: the app slot that receives traffic, or NULL when nothing is live. |
| Idle slot | The other app slot. It keeps running, connected to the shared data, ready to switch back to. |
| Lead slot | The slot a data job starts with its live `start` (D16): the active slot, or with none, the app slot whose deploy finished last. |
| Stale slot | An app slot stopped by a data job (D16), discarded after a failed deploy (D17), or whose release can't run the data: `slot_state.stale` set. Activate refuses it; a successful deploy to it clears the mark. |
| Route | A public hostname of the environment: `{hostname, service, container, follows: active \| server, tls_mode, health}`. Routes of `data.server.services` follow the data server; the rest follow the active slot. |

Shapes:

| Shape | data_mode | App slots | Data server | Traffic |
|---|---|---|---|---|
| Single | `slot` | `blue` | no | in place; follows `blue` |
| Single with a data server | `server` | `blue` | `data` | in place; app names follow `blue`, data names the server |
| Blue/Green | `server` | `blue`, `green` | `data` | Activate moves app names; data names stay on the server |

A single-slot `server` environment can gain a second slot (§9.8); a `slot` environment can't (its data would have to move).

Constraints: `Index("ux_environments_name_live", "name", unique=True, postgresql_where=deleted_at IS NULL, sqlite_where=…)`, `CHECK ((status = 'deleted') = (deleted_at IS NOT NULL))` (`ck_environments_deleted`), `CHECK (data_mode IN ('slot','server','managed'))`.

### 3.2 `instances` additions (instance.py:66-173)

| column | type | notes |
|---|---|---|
| environment_id | Uuid FK environments RESTRICT, index | NULL for standalone instances |
| slot | String(8) NULL | `blue`, `green`, `data` |
| slot_state | JSON NOT NULL server_default `'{}'` | `{last_check: {ok, at, deployment_id, results: [{hostname, code \| error}]} \| null, stale: {reason, at, deployment_id} \| null}` |

Constraints: `UniqueConstraint(environment_id, slot)` (`uq_instances_environment_id_slot`), `CHECK ((environment_id IS NULL) = (slot IS NULL))` (`ck_instances_slot_pair`). Relationship `environment` (lazy `selectin`). A slot instance gets `name = "<env> <slot>"`, `slug = "<env>-<slot>"`, `build_source = app`, the environment's repository, branch and manifest path, and `deploy_dir = NULL` (so `<deploy root>/<slug>`).

**Reserved slugs.** `<env>-blue`, `<env>-green` and `<env>-data` are reserved for every live environment, whether or not the slot exists yet: `POST /instances`, a slug change in `PATCH /instances/{id}` and the unmanaged-instance claim (`api/v1/unmanaged.py`) answer 409 `<slug> is reserved for environment <env>'s <slot> slot`, and Add slot checks again that no instance holds the slug (`environments.reserved_slug(db, slug) -> (env, slot) | None`).

### 3.3 `deployments` changes (instance.py:176-232)

| change | notes |
|---|---|
| `instance_id` becomes nullable | environment-level kinds (D9) |
| `environment_id` Uuid FK environments SET NULL, index | set on every job of an environment member and on every environment-level job |
| `CHECK (instance_id IS NOT NULL OR environment_id IS NOT NULL)` | `ck_deployments_subject` |
| `Index("ux_deployments_one_active_env", "environment_id", unique=True, where status IN ('queued','running') AND kind <> 'activate')` | I2; NULLs never conflict, so standalone instances are unaffected |
| `Index("ux_deployments_one_active_activate", "environment_id", unique=True, where status IN ('queued','running') AND kind = 'activate')` | I2: one activate at a time |
| `kind` gains `activate`, `publish`, `discard`, `remove_slot`, `teardown` | String(16) already fits |

The indexes can't express "an activate only beside a backup or a read-only snapshot"; `queue_job` checks that (§8.2), and the runner keys serialise anything a race let through, so an activate queued beside a deploy waits for it and its `check` step then runs against what the deploy left.

`options` gains, per kind: `go_live`, `chain`, `slot` (target slot name), `from_slot`, `back` (activate is a switch back), `switch` (the switch record, §10.2 step 2), `then` (`teardown` after a snapshot), `forget_traffic` (teardown retry), `snapshot` (teardown: the snapshot name taken first), `slots_were` (data jobs: what `stop_slots` stopped), `lead` (data jobs: the lead slot), `behind_ok` (a slot deploy confirmed past the D7 lag check), `after` (the job whose success queued this one), `seed` (activate: run starter content after the switch). `relationship("instance")` stays; code that reads `dep.instance` must handle None (listed in S8a, S9 and S11).

### 5.1 Grammar

```yaml
services:
  api: {port: 8000, port_var: STACK_API_PORT, hostname: "api.{STACK_DOMAIN}", health: /healthz}
  # health: optional; the path smoke tests request (default "/"). ^/[A-Za-z0-9._~/%?&=+-]{0,199}$. Needs hostname.

data:
  migrations: expand_contract       # optional; the previous release runs on the schema the next one migrates.
                                    # Required for two app slots (D7).

  attach:                           # optional; how the app runs on a host that doesn't hold its data
    needs:                          # the data endpoints it reads: 1-4 names, each a kind
      db: postgres
      objects: s3
    env:                            # 1-40 keys; written into every app slot's .env when the data isn't on the slot

  server:                           # optional; how the app's own data services run alone on a data server
    services: [spaces]              # services that run there; their hostnames follow the server
    ports:                          # published ports only the server has: 0-8, name ^[a-z][a-z0-9_]{0,30}$

    volumes:  ["ss-{STACK_ENV}-db_pgdata", "ss-{STACK_ENV}-storage_seaweeddata"] # which data.volumes live there
    commands:                       # replace these commands on the server: build, start, stop, has_data, data_up
      start:    [deploy/stack/ss-stack, data, "{slipway.env_dir}"]
      has_data: [deploy/stack/ss-stack, has-data, "{slipway.env_dir}", --server]
    provides:                       # each data.attach.needs endpoint, every field of its kind
```

**Endpoint kinds and their fields:**

| kind | fields | secret fields |
|---|---|---|
| `postgres` | `host`, `port`, `database`, `user`, `password`, `tls` (`disable` or `require`), `ca_b64` (may be empty; with `tls: require`, a CA means the server's certificate and name are checked) | `password` |
| `s3` | `endpoint`, `region`, `bucket`, `access_key`, `secret_key`, `path_style` (`true`/`false`) | `secret_key` |

A secret field's `provides` value must be exactly one `{secret.<KEY>}`, so Slipway knows which environment secret it is (phase 4 creates the managed database's role with that secret, as Sirdar's `do_provision.py:945-961` does). `tls` has two values because apps map it straight onto their own setting and the common ones (ServerSherpa's `STACK_DB_SSLMODE`, `ss-stack:273-276`) know only `require` and `disable`; certificate checking is the app's job when `ca_b64` is set.

**Template values added** (only where listed; elsewhere they are refused):

| Value | Allowed in | Filled with |
|---|---|---|
| `{data.<need>.<field>}` | `data.attach.env` | what the environment provides: the data server's rendered `provides` (phase 3), a managed resource (phase 4). A secret field (`password`, `secret_key`) makes the value a **secret value** |
| `{secret.<KEY>}` | `data.attach.env`, `data.server.provides` | the environment's secret. A value that uses one is a **secret value**: kept out of `public_env`, hidden in logs (`ssh.Redactor`), never stored in `app_state` |
| `{server.host}` | `data.server.provides`, `data.server.env` | the data server host's `upstream_address` |
| `{server.port.<name>}` | `data.server.provides`, `data.server.env` | the host port the data server got for `server.ports.<name>` or for a service in `server.services` |
| `{server.clients}` | `data.server.env` | the app slots' hosts' `client_address`es (`lan_address or upstream_address`, §3.5), sorted, unique, comma-separated |
| `{slipway.environment}`, `{slipway.slot}` | every template | the environment's name and the slot (`blue`, `green`, `data`); empty for standalone instances. Added to `BUILTINS` (manifest.py:92) and `app_builtins` (deployer.py:2441) |

An `attach.env` value that renders to the empty string is **left out** of the `.env` (the env_file's own line, if any, stays as written), so one `attach` serves a data server without a CA and a managed database with one.

### 5.2 Validation (all raise `ManifestError("slipway.yml: <where>: <message>")`)

## 6. Settings, secrets and identity across slots

**Where each value comes from** when a member job renders its `.env` (`_start`, deployer.py:1659-1761, and `_install_app`, :2612-2781):

| Input | Standalone instance | Environment member |
|---|---|---|
| `settings`, `chosen` services | `instance.app_settings`, `app_services` | `environment.app_settings`, `app_services` |
| secrets | `instance.app_secrets` | `environment.app_secrets` (D5) |
| own variables | `instance.env` | `environment.env` |
| `data_values` (slot role) | — | the data owner's rendered `provides` (below) |
| `server_values` (server role) | — | host = own host's `upstream_address`, clients = the app slots' hosts' `client_address`, ports from this job's port plan |
| live inputs (P2 D3) | `app_state.live` of the instance | `app_state.live` of the instance (each member keeps its own) |

**`data_values`** = `environments.data_values(env, owner)`: render `data.server.provides` with the data owner's live render (P2 `_live_plan`: its `app_state.live` settings, host ports and today's paths) plus `{server.host}` = owner host `upstream_address`, `{server.port.*}` = owner `app_state.live.host_ports`, `{secret.*}` = environment secrets. Refusals, checked at queue time (409) and again in the slot's `settings` step:

- the owner has no live release: `Deploy <env>'s data server first: the app slots need its address and ports`;
- the slot's host isn't in the owner's `app_state.live.clients`: `<env>'s data server doesn't let <host> (<address>) in yet: update the data server first (Deploy → Data server)`;
- an address isn't an IP literal (D18): `Host <name>'s address is <x>; <env>'s data server lets clients in by IP address: set the host's LAN address (or proxy address) to its IP`.

**Reaching the data from the slot.** For each `postgres` need, the slot's `settings` step (after the `.env` is written, before `build`) runs, on the slot's host, `docker run --rm -e PGPASSWORD postgres:16-alpine psql "host=<host> port=<port> dbname=<database> user=<user> sslmode=<tls> connect_timeout=10" -tAc 'select 1'`, the password reaching docker through the environment, never argv. It uses Docker's default bridge, so the connection leaves the host the way the app's does. A failure stops the job before anything restarted: `<blue> on <host> can't sign in to <env>'s database at <host>:<port> (<psql's last line>). If it says "no pg_hba.conf entry for host <a>", set host <name>'s LAN address to <a> and update the data server`. An `s3` need is not probed (it goes through Switchyard, §10). The probe runs only for mode `server` slots; `postgres:16-alpine` is the image ServerSherpa's own client uses (`ss-stack:50`), so it is usually there already.

**Secrets.**
- Created with the environment from slipway.yml at the branch head (`manifest.new_secrets`, manifest.py:1201) and saved in `environments.app_secrets` in the create transaction.
- A member job whose release declares a secret the environment lacks generates it in `_install_app` and saves it with `UPDATE environments SET app_secrets = :new, secrets_version = secrets_version + 1 WHERE id = :id AND secrets_version = :read` (compare-and-set on the version read with the secrets; a row count of 0 fails the step `<env>'s secrets changed while this job ran; retry it`). Every other write of `app_secrets` (PATCH of a variable that replaces a secret, an identity override in `restore`) bumps `secrets_version` in the same statement. The runner keys (D8) mean a mismatch only follows a manual edit.
- A variable of the environment with a secret's name replaces it and is kept as the secret, as for instances.
- `_hide_instance_values` (deployer.py:1771) hides the environment's secrets and variables and every `AppPlan.secret_values` entry (`SS_DATABASE_URL`, `SS_SPACES_SECRET_KEY`).
- `GET /environments/{id}/env` (environments:write) returns the variables, as `GET /instances/{id}/env` does; secrets are never returned.

**Identity.** The data's identity keys are environment secrets (`identity: true`); `live_identity` is on the data owner (D3). Every identity value a member job computes comes from `AppPlan.identity` (§5.3), i.e. the environment's secrets with the environment's variables over them, never from the data server's blanked `.env` lines.
- Set at the `finish` of the data owner's first job that created data, and by every member job's `finish` when it is unset (the values equal the environment's).
- Changed only in the `restore` step of a job on the data owner (snapshot or override, P2 I3), which writes `environments.app_secrets` (bumping `secrets_version`) and `owner.live_identity` in one transaction. `_apply_override` (deployer.py:4065-4095) re-renders the server's `.env` (still blank for these keys) and takes `effective` from the re-plan's `AppPlan.identity`. The lead slot is re-rendered by `start_slots` (§7.4); the other slot becomes stale (D16).
- `_identity_problem` (deployer.py:2846) compares `AppPlan.identity` of the live render with `owner.live_identity`, for jobs on the owner and on app slots alike.
- `Backup.identity` is taken from `owner.live_identity` as in phase 2; when it is unset, from `AppPlan.identity` (deployer.py:3308-3311). A snapshot's identity likewise.

**Settings edits** (PATCH) reach each member on its next deploy. The environment page says `<blue> keeps the settings it was deployed with until you deploy to it` when they differ (`app_state.live.settings` vs the environment's).

## 7. Data in an environment

### 7.1 Where things run (mode `server`; mode `slot` is phase 2 on the slot)

| What | Host | Release and `.env` |
|---|---|---|
| `has_data`, `data_up`, `dump`, `verify_dump`, `revision`, `restore`, `export_files`, `import_files`, `after_import`; volume probes and Reset of `server.volumes` | data server | the data server's live release, server role (P2 D3 live render) |
| `accepts` | the app slot that will run the data next: the deploying slot's new release (deploy), the lead slot's live release (restore kinds); also the **active** slot's live release before an idle slot's `start` (the D7 lag check, §7.6) | slot role |
| `first_admin` | the slot that just started (deploy), or the lead slot (admin, reset) | slot role |
| `seed` | the slot that just went live, in the environment's first Activate (D24); the active slot (content, reset) | slot role |
| Reset of slot-local volumes (`data.volumes` minus `server.volumes`) | each app slot | slot role |
| Stop and start around a data job | each app slot: `docker compose stop` on its projects (P2 D17); the lead slot is started again with its live `start` (it migrates), the other with `docker compose start` or not at all (D16) | slot role |

Every data command keeps phase 2's guarantees (P2 §3.1), the host lock of the host it runs on (P2 §4.5) and its timeouts.

**Members.** `_AppRun` (deployer.py:2544) holds one instance's session, paths and lock. Cross-host work uses `_Member(instance, remote, paths, side)`: an instance of the environment, an SSH session opened with the job's `connect` factory (tests use one keyed on the target hostname, §16.1), its `paths_for(instance)` and its live (or new) release. `_AppRun` gains `members: dict[str, _Member]` (by slot name, opened lazily and closed when the job ends) and `member(slot) -> _Member`. `_app_run`, `_accepts`, `_acquire_lock`/`_release_lock` and the `stop`/`start` helpers take an optional `member`; without one they act on `c.instance` as today. Every command run through a member takes **that** member's host lock (`.slipway-lock` in its folder) with the job's id, so a job on the owner that runs `accepts` on blue holds blue's lock for that command.

**The migration lock.** A slot's `start` migrates the shared database, but phase 2 writes the `d` flag (P2 §4.5) only into the lock of the host the command runs on. For an app slot in mode `server`, the slot deploy also writes a `d` line for the same job into the **data owner's** lock (over the owner member's session) before `start` and removes it after `start` returns. A command left running (timeout, Slipway restart) leaves both lines, so the owner's next job (Back up now, a restore, the data server deploy) waits or refuses exactly as phase 2 does for a left lock.

### 7.2 Backups

- Taken on the data server into `<data server folder>/backups/` by the data owner's dump commands, before: every slot deploy (`pre_deploy`), every data server deploy, every restore, roll back and reset (`pre_*`), and Back up now. `Backup.instance_id` is the data owner; `deployment_id` is the job that took it (a slot deploy's id, say). `Backup.release`, `format` and `commit_sha` are the data server's live release (the one whose `dump` ran), as phase 2 records them for the instance that ran the dump; `commit_sha` is shown only and feeds no rule (data.py:404). The Backups card adds a "Taken by" column (`Deploy to green`, `Back up now`) from the deployment.
- Retention (`keep_backups`), pinning, checks, `?check=true` and Delete are phase 2's, on the data owner.
- The pre-deploy backup in a slot deploy runs the data server's **live** release's `data_up`, `revision`, `dump` and `verify_dump` (P2 D4) through the owner member, then the deploying slot's new release runs `accepts` on the revision (P2 `_check_new_revision`, deployer.py:3225) on the slot's host, and, with two app slots and an active one, the active slot's live release runs `accepts` on the same revision (the lag check, §7.6).
- A slot deploy on a never-live environment skips it with `No data yet` when the owner's `has_data` answers 3.
- Retry inheritance (P2 D11) is decided against "the latest changing job" of the **environment** (§7.5).

### 7.5 Dirty state, hold and "latest"

- `data_dirty` and the hold live on the data owner. A **slot deploy** that fails after `start` began marks `owner.data_dirty` (first = that deploy, backup = its pre-deploy backup); a failed restore, roll back or reset on the owner sets it as P2 §8.4.
- While `owner.data_dirty.hold`: refused with the hold text — deploys to any member, `activate`, `discard`, control start and restart of any app slot, Take snapshot, admin and content. Allowed: retry, restore, reset, roll back, Back up now, remove a slot (not the one the dirty state names), delete.
- While `owner.data_dirty` is set at all: `activate` is refused (`<env>'s data may not be what <slot> expects since <deployment d8> failed: discard or retry it first`), except an activate of the recorded active slot while a switch is unresolved (it restores the known state). Removing the slot whose job the dirty state names is refused (`Discard <green> or roll back first`), since its deployments, which the dirty state points at, would go with it.

**Who writes the owner's phase 2 fields.** Every write below goes to `owner_of(instance)`; an app slot's own row gets only `status`, `current_commit_sha`, `last_deployed_at`, `app_state`, `published_ports`, `slot_state` and `proxy_entries` (unused for members). The table is for mode `server`; in mode `slot` the owner is the slot, and phase 2's rules apply to it unchanged.

| Event | Owner's fields |
|---|---|
| Slot deploy fails or is interrupted after its `start` began (`_failure_fields`, `_recover_instance`) | `data_dirty` marked (first = that deploy) |
| Slot deploy succeeds (`_success_fields`) | `live_identity` when unset; `fresh_data` and `seed_snapshot_id` cleared; `data_dirty` cleared **only** when its `first` is a deploy of this same slot (a retry, or a new deploy of the slot that failed) |
| Data server deploy succeeds | `live_identity` when unset (from `AppPlan.identity`), `fresh_data`, `seed_snapshot_id`; `data_dirty` is never cleared by it (it ran no app migration) |
| Data server deploy fails after its `start` began | `data_dirty` marked, as P2 |
| Restore, roll back, reset on the owner succeed (after `start_slots`) | as P2: `data_dirty` cleared, `live_identity` per the restore |
| Restore, roll back, reset fail or are interrupted after a change began (`start_slots` included) | as P2 §8.4: `data_dirty` with the hold |
| `discard` succeeds | `data_dirty` cleared |
| `_cache_elsewhere`, `_save_instance(fresh_data=…)`, `content_pending` writes, `last_control_at` | the owner |

- "Latest changing job" (P2 D10) is the newest deployment with `environment_id = env` and kind in `CHANGING_KINDS`, whichever member it ran on (`data.latest_changing_job`).
- `owner.last_control_at` is set by a control start or restart of **any** app slot (P2 §8.1 retry rule).

`_success_fields` and `_failure_fields` return `(instance_fields, owner_fields)` for members; `_finish` (deployer.py:1348) writes both in its one transaction, and, for an environment-level job (`instance_id` NULL, where it returns early today), updates the deployment row alone.

### 7.6 Migrations with two slots

- Two app slots need `data.migrations: expand_contract` (D7): `POST /environments` and Add slot answer 409 `<repo>'s slipway.yml at <branch> doesn't declare data.migrations: expand_contract. With two slots, <blue> keeps running on the database <green> migrates, so its migrations must add before they remove.`
- The Deploy dialog says: `<blue> keeps serving while <green> migrates the database. <app>'s slipway.yml says its migrations are expand/contract: add columns and tables first, remove them in a later release.`
- Redeploying an older commit on a migrated database is still refused by `accepts` (P2), so Switch back (no `start`) is the way back.
- **The lag check.** Expand/contract holds between adjacent releases. After a switch back, the active slot (N) runs on a database the idle slot (N+1) migrated; a deploy of N+2 to the idle slot may contract what N still uses. So a deploy to the idle slot, with an active slot and data, runs the **active** slot's live `accepts` on the current revision (read in the `backup` step) before the idle slot's `start`. An answer of 3 fails the step before `start`, unless the deploy was queued with `behind_ok`: `<blue> (<sha7>) already runs on a database migrated past it (revision <r>, by <green>'s <sha7>). A new release may remove what <blue> still uses. Activate <green> again and deploy to <blue>, or deploy again confirming that this release removes nothing <blue> uses.` The API takes `{acknowledge_schema: true}` and the Deploy dialog shows the checkbox `This release removes nothing <blue> (<sha7>) uses` when `actions.deploy.behind` is true: the last activate was a switch back (`traffic_state.last.back`) and no deploy to the idle slot has succeeded since. That hint only decides whether the checkbox shows; the run-time `accepts` answer decides the refusal, and a refused deploy's error offers **Deploy again, confirming**. The fix-and-redeploy loop after a switch back (same migrations, a code fix) passes with the checkbox.

### 8.2 Locking

1. `data.runner_keys(instance, kind=None, options=None) -> tuple[Hashable, ...]`: `(instance.id,)` for a standalone instance (today's behaviour); for a member, `data.env_keys(environment_id, kind, options)`, which is `((env, "data"),)` for the owner's `backup` and for a `snapshot` without `stop_app`, `((env, "traffic"),)` for `activate`, and `((env, "data"), (env, "traffic"))` for everything else (sorted, so two jobs never take them in opposite orders). `data.data_scope_key(instance)` (data.py:236, unused today) is replaced by it.
2. `DeployRunner` (deployer.py:4951-5040) keys its locks, `_pending`, `_exclusive` and `_deleting` on these keys. `submit(deployment_id, keys)` acquires each key's `asyncio.Lock` in order; `busy(keys)` is true when any key is pending or exclusive; `exclusive(keys, deleting=False)` and `is_deleting(keys)` likewise. A non-job change (control, backup delete, `?check=true`, the deploy-root move) on a member uses both of its environment's keys. **Every call site changes in the same slice (S8a)**, so the tests pass at each slice's end: `api/v1/instances.py` (`queue_deployment`'s `submit` at :265, the submit at :368, every `exclusive` at :403, 432, 526, 646, 948, 1048, 1290, 1314, and `is_deleting` at :217), `api/v1/hosts.py:213` (deploy-root move: the keys of each instance on the host), `api/v1/unmanaged.py:275`, `services/data.py:1266`, and the chain hook; `api/v1/deployments.py`'s retry and rollback reach the runner through `queue_deployment`. Environment-level jobs use `env_keys(env.id, kind, options)`.
3. `services/jobs.py` `queue_job` (§8.5) refuses when `data.active_job` for the instance exists, or when `data.active_env_jobs(db, env_id)` holds a job whose keys meet the new job's: `A job is already running for <env> (<Kind> on <slot>); wait for it to finish`. So an `activate` queues beside a running Back up now; a deploy doesn't.
4. `ux_deployments_one_active` (per instance), `ux_deployments_one_active_env` and `ux_deployments_one_active_activate` (per environment, §3.3): an IntegrityError on any becomes that 409.
5. Host locks (`.slipway-lock`) stay per instance folder; a job that runs commands on another member's host takes **that** member's lock for each command (§7.1 Members), and a slot `start` writes a `d` line into the owner's lock (§7.1).
6. Port planning (`_host_port_locks`, deployer.py:1843) is per host as today; slots on one host get distinct ports.
7. `switchyard._lock` (switchyard.py:316) serialises Switchyard writes across Slipway. It is held for a plan-and-apply and again for a put-back, never across the public check or a wait (§10.2), so a switch doesn't stall other instances' `proxy` steps for minutes.

### 8.4 Step lists

`deployer.steps_for(instance, kind, …)` gains environment-aware lists; standalone instances take today's branches (I1). `environments.env_steps_for(env, kind, options)` builds the environment-level lists. ⟨…⟩ marks a step listed only when its condition, known at queue time, holds.

- **deploy, data server:** `resolve, source, upload, manifest, ports, settings, build, ⟨check⟩ˢ, backup, ⟨stop, restore, files, after_import⟩ˢ, start, finish, ⟨dns⟩ᵈ, traffic, ⟨smoke⟩ˡ`

- **reset (owner, mode `server`):** `release, manifest, settings, build, ⟨check⟩ˢ, backup, stop_slots, stop, reset, ⟨restore, files, after_import⟩ˢ, start, ⟨start_slots⟩ᵍ, finish, ⟨first_admin⟩ᵃ, ⟨seed⟩ᵒ, traffic`
- **reset, Start over (owner, mode `server`):** `release, backup, stop_slots, stop, reset`
- **snapshot (owner, mode `server`):** `release, ⟨stop_slots⟩ᵗ, export, ⟨start_slots⟩ᵗ, store, ⟨restop⟩ᵖ` (here `start_slots` uses `docker compose start` for both slots)
- **backup, admin, content:** P2 lists (admin and content on the active slot).
- **activate:** `check, ⟨start_slot⟩ʳ, smoke, ⟨dns⟩ᵈ, switch, ⟨seed⟩ᵏ`
- **publish:** `check, ⟨traffic⟩ʷ, ⟨dns⟩ᵈ`
- **discard:** `check, stop_slot, smoke, settle`
- **remove_slot:** `check, slot`
- **teardown:** `check, unroute, undns, slots, data_server, forget` (`unroute` skipped when `traffic.switch` is `none` and no `proxy_host` rows exist; `undns` when no `dns_record` rows exist)

Conditions as P2 §7.3 (ᵃ ˢ ᵉ ᶠ ᵒ ᵗ ᵖ, evaluated on the **data owner**), plus: ʳ the target slot is STOPPED; ᵈ `traffic.dns` is set; ᵍ an app slot has been deployed; ˡ an app slot is active; ʷ `traffic.switch` isn't `none`; ᵏ this is the environment's first activation (status `new`) and `owner.seed_content` is set (D24); a `seed` that fails or is cut off leaves `owner.content_pending`, as P2. In a slot deploy, ᵃ holds only for the first app slot deploy that starts on the empty data (`owner.fresh_data == "empty"` and no app slot has finished a deploy yet); ᵉ never holds for a member's deploy: a new environment seeds at its first Activate (D24) and a reset seeds itself (ᵒ), so the `seed` row is dropped from both slot deploy lists.

`PRE_START_STEPS` gains `stop_slots`. A new `PRE_FINISH_STEPS = ("start_slots",)` runs between `start` and `finish`; it is a change step, so its failure fails the job before anything counts as live. `smoke`, `dns` and `traffic` of a member deploy run after the post-finish steps and never fail the job (P2 D12). Execution follows the listed rows in order (P2 §7.2). `_settle_after_live` (deployer.py:4782) gives a member's `traffic` row the note `Use Publish names on the environment page to update Switchyard` instead of the instance page's Sync proxy (which answers 409 for members).

### 8.5 Go-live and the chain (`services/environments.py`)

- `target_slot(env)`: the app slot that isn't active; with nothing active, `blue`; with one app slot, that slot (in place).
- `goes_live(env, slot)`: nothing is active, or `auto_activate` is on and there are two app slots. With one app slot, a deploy after the first is in place (`traffic` syncs; no activate).
- `queue_job` records `options.go_live` and `options.slot` on a slot deploy and, when `go_live` and there are two app slots (or nothing is live), requires `traffic:switch` of the user.
- `after_job(deployment_id)` is called on success for any deployment with `environment_id`, from the end of `run_deployment` and of `env_jobs.run` (not from `_finish`, which also records successes during shutdown). In its own session, under no runner lock (it only queues):
  1. a data server deploy with `options.chain`, and no app slot has finished a deploy → queue a deploy of `target_slot(env)` (`options.chain`, `go_live` true);
  2. an app slot deploy with `options.go_live` → queue `activate` of that slot (`options.chain`);
  3. a snapshot with `options.then == "teardown"` → queue `teardown` with the stored `confirm` already checked (`options.confirmed = true`).
  (An `activate` sets status `live` itself, §9.5 step 6.) The new job is `triggered_by` the finished job's user and carries `options.after = <finished id>`. A refusal (busy, hold, unpinned host, a permission the user no longer has) is written to `environments.notice` and audited (`environment.chain_stopped`); the page shows it with the button that starts that job by hand. Calling `after_job` twice for one deployment queues once (it looks for a job with `options.after == <id>`).
- **Shutdown and restart.** A job that `_end_after_live` records as succeeded because Slipway is shutting down (the `CancelledError` path, deployer.py:4902, 4935) does not call `after_job`; it writes `notice = {text: "Slipway stopped after <job> succeeded, before it started <next>", deployment_id, next: {kind, slot}}`. `recover_interrupted` does the same for every environment job `_recover_live` marks succeeded (deployer.py:5083) whose chain rule would have queued a follow-up, since that job has no Retry. The notice's button queues the follow-up by hand (`POST /environments/{id}/notice/continue`, the follow-up's own permission), and is cleared by it or by any later job of the environment.

`services/jobs.py` (new) holds `queue_job(db, *, instance=None, environment=None, user, kind, retry_of=None, options=None, **refs) -> Deployment`, moved from `api/v1/instances.queue_deployment` (instances.py:207-258) and raising `JobRefused(status, text)`; the API's `queue_deployment` becomes a wrapper turning it into `HTTPException`. For members it sets `environment_id` and applies §7.5 and §10.6's fences.

## 9. Flows

Every flow lists its refusals (each answered before anything changes, I5), its steps, what a retry does and what is recorded. Refusals are 409 unless marked; typed-name mismatches are 422 and are checked first (P2 §13).

### 9.1 Create environment (`POST /environments`)

**Refusals** (`environments.validate_create`, in this order):
1. `name`: the §2 pattern (422 `Use 2-26 lowercase letters, digits and hyphens, starting with a letter`); a live environment has it (`An environment named <name> already exists`); an instance has slug `<name>-blue`, `-green` or `-data` (`Instance <x> already uses the slug <slug>; pick another name`). The slugs are then reserved (§3.2).
2. The repository is synced and slipway.yml at `branch` reads and parses (read with `repos` the way `GET /repositories/{id}/manifest` does, repositories.py:90): the parse error, or `<repo> has no <path> at <branch>`.
3. Shape: two app slots need `capabilities` `bluegreen` (`server` and `migrations`: the §7.6 text, or `<repo>'s slipway.yml doesn't describe a data server (data.server), so Slipway can't run two slots on one set of data`); mode `server` needs `server`.
4. Hosts: each exists and is pinned (`Check host <name> first: Slipway hasn't verified its key`); mode `server` app-slot hosts' `client_address` are IP literals (§6). The data server on an app slot's host is refused (`The data server needs a host of its own: a container on <host> reaches its database from a Docker address, which <env>'s data server can't let in by host address`). Two app slots on one host are accepted with a warning in the response (`warnings[]`).
5. Settings: required ones set, values valid (`manifest.plan` in each role with placeholder ports, which also catches clashing variables).
6. Names: the planned hostnames (§10.1) are unique against live environments' `hostnames` and against every standalone instance's `routes` and `app_state.routes` (`<hostname> is already a hostname of instance <x>` / `of environment <y>`).
7. Traffic: `switch = switchyard` needs Switchyard configured (`Set up Switchyard in Settings → Integrations first`); two app slots need `switch = switchyard`; `dns` set needs Cloudflare configured and every hostname inside its zone (`<hostname> isn't in the Cloudflare zone <zone>`).
8. Seed snapshot: ready, same `data.app`, permissions per §4.1 (403 otherwise); a first admin is required when starting empty and the manifest declares one (422 `Enter the first admin`), checked with `first_admin_problem` (deployer.py:3442).

**Writes** (one transaction): the environment (status `new`, secrets generated, `hostnames`), its instances (`blue`, `green` when asked, `data` in mode `server`; status CREATED), the data owner's phase 2 fields (`keep_backups`, `seed_snapshot_id`, `seed_content`) and its `FirstAdmin` row; audit `environment.create`. No host is touched.

**`?check=true`** runs the refusals and returns `200 {ok, warnings, plan: {slots, hostnames, secrets: [names], traffic}}` with no write. Every 422/409 body is `{"detail": "<text>", "field": "<field>"}` so the flow page can jump to the step that holds the field (§12.3).

### 9.2 First deploy (`POST /environments/{id}/deploy` on a `new` environment)

1. Mode `server`: queue a data server deploy with `options.chain`. Mode `slot`: queue a deploy of `blue` with `options.chain`, `go_live`.
2. Data server deploy: settings (server role, clients = the app slots' hosts), build, check/stop/restore/files/after_import when seeding (`stop` is `ss-stack down`, db and storage only with S7), `backup` (skipped `No data yet`), `start` (`ss-stack data`), `finish` (`app_state.live` with `clients` and `host_ports`; `live_identity` from `AppPlan.identity`), `dns` (every route's record at the fixed address, when DNS is on), `traffic` (creates the **server-following** hosts, `spaces.<domain>` → the data server, and runs the public check on them; warnings only). No app name is routed yet.
3. Hook → deploy of `blue` (`go_live`): settings (slot role with `data_values`; the database probe), build, `backup` (owner: `No data yet` or a real dump when seeded), `start` (migrates the shared database; `d` line in the owner's lock), `finish`, `first_admin`, `smoke`, `traffic` (skipped: not active yet). No `seed` (D24).
4. Hook → `activate` of `blue` (§9.5): `dns` (every record already there: nothing to do), `switch` creates the active-following Switchyard hosts (app names → blue), checks them through Switchyard (12 rounds: Caddy is getting certificates), records `active_slot_id`, status `live`; then `seed` on blue (starter content, now that `spaces.<domain>` and the app names are served).

Mode `slot` runs 3 and 4 only (blue holds its own data); `spaces.<domain>` follows blue and is created by the switch, before `seed`.

A failure anywhere stops the chain; Retry of the failed job continues it (the hook runs on its success). Refusals are those of each job.

### 9.3 Deploy to the idle slot (`POST /environments/{id}/deploy {target?: "slot" | "data", slot?}`)

**Refusals:** environment `deleting`/`deleted`; a job running (§8.2); the owner's hold (§7.5); an unresolved switch (§10.6); `slot` given and it is the active one while two app slots exist (`<blue> serves traffic: deploy to <green>, then activate it`); the slot's host unpinned; `data_values` refusals (§6); `go_live` without `traffic:switch` (403). At run time: the database probe (§6), the lag check (§7.6), and, in the `manifest` step, the release's hostnames against standalone instances' routes and other live environments' `hostnames` (`<hostname> is already a hostname of instance <x>`; the step fails before anything starts). A name the release adds is written into `env.hostnames` at `finish`.

**Body:** `{target?: "slot" | "data", slot?, acknowledge_schema?: bool}` (`acknowledge_schema` sets `options.behind_ok`, §7.6).

**Steps:** §8.4's slot deploy list. The slot's `slot_state.stale` is cleared at `finish`; `traffic_state.last_slot_deploy` is set then. A stale target is deployed as any other; the Deploy dialog adds `<green> was <stale reason>; this deploy brings it up to date.`

**Retry:** P2 §8.1, with "latest changing job" across the environment; the release and build are reused on the same slot; the pre-deploy backup is inherited when `start` began.

**Recorded:** the deployment (`environment_id`, `options.slot`, `go_live`), `slot_state.last_check`, the owner's backup row, audit `deployment.create` with environment and slot.

### 9.4 Smoke test

Runs as `smoke` in every app slot deploy (warning-only) and in Activate (failing). §10.8 has the commands. Nothing is changed; results go to `slot_state.last_check` in their own transaction.

### 9.5 Activate (`POST /environments/{id}/activate {slot}`)

**Refusals (`check` step, also answered by the API before queueing):**
1. no such app slot, or it is the data server (`Only an app slot can take traffic`);
2. it is already active and no switch is unresolved (`<green> already takes the traffic`);
3. it never finished a deploy (`Deploy to <green> first`); its latest deploy didn't succeed (`<green>'s latest deploy (<d8>) failed: retry it, deploy again or discard it`); it is stale (`<green> was <stale reason>; deploy to it first`); its status is neither RUNNING nor STOPPED (`<green> is <status>`);
4. its host is unpinned; the owner's hold, or the owner's dirty state at all (§7.5; except the recorded active slot while a switch is unresolved); a job running whose keys meet `(env, traffic)` (§8.2);
5. the switch backend isn't configured (`Set up Switchyard in Settings → Integrations first`);
6. the switch plan (§10.2, read-only) has blockers: the list, `Slipway changed nothing`.

**Steps:**
1. `check` (above, again at run time).
2. `start_slot` (when STOPPED): `docker compose start` on its projects.
3. `smoke` on the slot's host; any failing name fails the step with the codes: `api.uat.example.com answered 502 on /healthz (5 tries)`. Nothing has changed.
4. `dns` (when listed): the §10.5 publisher. Records are fixed-address, so publishing them before the switch moves no traffic, and Caddy can get a certificate for a name only once its record exists. When the plan has a record to **create** (a name with none), a failure fails the step and the job before any traffic write (`Traffic stays on <blue>`). When every record exists and only updates or nothing remain, a failure is a `warning` and the switch goes ahead (a Cloudflare outage never blocks a switch back).
5. `switch`: §10.2-10.3, one step: plan, apply, then the verify phase (the public check through Switchyard, §10.8), and on any failure the put-back. It fails with `Traffic stays on <blue>` (or `Nothing was live before`), or with the unresolved text (§10.6).
6. After the verify phase, still inside `switch`: in one transaction, `active_slot_id = slot`, `traffic_state.last = {…, back}`, `traffic_state.unresolved = NULL`, status `live`; audit `environment.activate`.
7. `seed` (ᵏ, the first activation only): the manifest's `seed` on the slot now live (P2 D12: a failure is a `warning` and leaves `content_pending`; Add starter content runs it again).

**Retry:** a new activate of the same slot, allowed while `options.from_slot` still equals the active slot (or a switch is unresolved); otherwise `Traffic moved since: activate again instead`. Needs `traffic:switch`.

### 9.6 Switch back

Activate of the slot that was active before (`traffic_state.last.from_slot`), with `options.back = true` for the label. The page offers it as **Switch back to <blue>** while that slot is deployed, not stale, and running. Everything else is §9.5. It may run beside a Back up now or a snapshot that doesn't stop the app (D8). No data changes: the database stays migrated (expand/contract, D7); the next deploy to the idle slot meets the lag check (§7.6).

### 9.7 Update the data server (`POST /environments/{id}/deploy {target: "data"}`)

**Refusals:** mode `slot`; §9.3's environment fences (hold, running job; an unresolved switch does **not** refuse it).

**Steps:** §8.4's server deploy list: the pre-deploy backup (its own data), `start` (`ss-stack data`; the dialog says `The database and file store restart if their images changed, and <blue> loses its connection for a moment`), `finish` (`clients` and `host_ports` recorded), `dns`, `traffic` (a sync of **server-following** hosts only, to the new ports, warning-only; it never plans an active-following host, so it can't move app traffic, I6), `smoke` of the active slot (warning-only: `<blue> answered 502 on /healthz after the data server restarted`). App slots keep running. A data server deploy never clears the owner's dirty state (§7.5).

The slots' `.env`s name the data server's current ports, so the `settings` step (before `start`) compares the new port plan with `app_state.live.host_ports` and, when a port that `provides` uses would move, fails `The data server's ports would move (<db 5432 → 5433>), and the slots' settings name the old ones: free the port on <host>, or recreate the slots`. Nothing has restarted. Ports normally stay put (`port_overrides` keep what a deploy chose, P1).

### 9.8 Add a slot (`POST /environments/{id}/slots {host_id, update_data_server?: bool}`)

**Refusals:** mode `slot` (`<env> keeps its data on <blue>; a second slot needs a data server`); two app slots already; `bluegreen` capability missing at the branch head (§7.6); the host unpinned, its `client_address` not an IP literal, or the data server's host; an instance holding the slug `<env>-green` (§3.2); a job running.

**Writes:** the instance `<env>-green` (CREATED) on the host; audit `environment.slot_add`. With `update_data_server`, queues §9.7 with `options.chain` so the hook then queues a deploy of the new slot (no `go_live`). Otherwise the page says `Update the data server so it lets <host> in, then deploy to <green>`.

### 9.9 Remove a slot (`DELETE /environments/{id}/slots/{slot}`, body `{confirm}`)

**Refusals:** confirm ≠ environment name (422); the data server (`The data server goes with the environment`); the active slot (`<blue> takes the traffic: activate <green> first`); the only app slot; the slot whose job the owner's dirty state names (`Discard <green> or roll back first`); a job running; an unresolved switch.

**Steps** (kind `remove_slot`): `check`; `slot`: `deployer.destroy(slot_instance)` (deployer.py:843: containers and folder go, `.env` is kept in `.slipway-kept`, volumes are never removed), then the instance row is deleted in its own transaction (its deployments cascade; this job's row has no instance and stays). If `destroy` finds leftovers it fails with them and keeps the row.

**Retry:** runs again; an already deleted row makes `slot` succeed with `Already removed`. **Recorded:** audit `environment.slot_remove`; the page adds `<env>'s data server still lets <host> in: update it to stop that`.

### 9.10 Delete the environment (`DELETE /environments/{id}`, body `{confirm, snapshot?: {name}}`)

**Refusals:** confirm (422); status `deleting` with its teardown running, or `deleted`; a job running; `snapshot` without `data:backup` (403) or the owner's snapshot refusals (P2 §10.4).

**With `snapshot`:** queue kind `snapshot` on the data owner with `options.then = "teardown"`; the hook queues the teardown when it succeeds. The status becomes `deleting` only when the teardown is queued.

**Steps** (kind `teardown`; status `deleting` when queued; audit `environment.delete`):
1. `check`: confirm was checked at queue time; refuses a running member job.
2. `unroute`: Switchyard mode `remove` (§10.3): every `proxy_host` row whose host still carries this environment's marker is deleted, then one apply. A host without the marker is forgotten, not deleted. With a blocker (foreign pending changes) the deletes are left staged and the step ends as `warning` (`Applied nothing: other changes were waiting in Switchyard; apply there`). Switchyard unreachable fails the step, unless the retry was asked with `forget_traffic: true` (typed name), which forgets the rows.
3. `undns`: Cloudflare remove (§10.5): created records still ours are deleted, claimed ones forgotten. Same failure and `forget_traffic` rule.
4. `slots`: each app slot, green first: `deployer.destroy`, then the row is deleted.
5. `data_server`: `deployer.destroy` of the data server: containers and folder go; **volumes stay**; `backups/` moves to `.slipway-kept` with its sidecars (P2 D18); then the row is deleted (its Backup and FirstAdmin rows cascade).
6. `forget`: `resources` for the environment must be empty (else the step fails naming them); `status = deleted`, `deleted_at`, `deleted_by_id`, `active_slot_id = NULL`.

**Retry:** idempotent steps; a deleted instance is `Already removed`. **The dialog** lists what goes (Switchyard hosts and DNS records Slipway created, with counts; the containers and folders of every slot and the data server) and what stays (claimed records; data volumes and backups on <data host>; images; snapshots on Slipway).

### 9.11 Publish names (`POST /environments/{id}/publish`)

Brings Switchyard and DNS up to date for what is live, without a deploy (the way back after a member job's `traffic` step was cut off or warned).

**Refusals:** neither `traffic.switch = switchyard` nor `traffic.dns` (`<env> publishes no names`); Cloudflare not configured when DNS is on; a job running; an unresolved switch when an active-following host would change (`Traffic may be split between the slots: activate a slot or resolve first`); the plans' blockers (each step fails with the list before any write). **Steps:** `check`; `traffic`: a sync (§10.3, mode `sync`) of server-following hosts to the data server and active-following hosts to the **recorded** active slot (only when one is recorded and no switch is unresolved; it never moves a host to another slot); `dns` (§10.5). **Retry:** runs again. **Recorded:** `resources` rows, audit `resource.*`.

Claim (`POST /environments/{id}/dns/claim {hostname}`, `traffic:switch`): when the name's status is `claimable` (exactly one A record nobody records), records it with origin `claimed`; audit `resource.claim`. No job.

### 9.12 Resolve an unresolved switch (`POST /environments/{id}/traffic/resolve {confirm}`)

Under `runner.exclusive(env.id)`, reads Switchyard (`GET /api/config/preview`, `GET /api/hosts`). If every active-following host owned by the environment sends traffic to one app slot's targets, sets `active_slot_id` to that slot and clears `unresolved`; audit `environment.resolve`. Otherwise 409 `Switchyard sends api to <blue> and portal to <green>: activate one of them`. Activating either slot also resolves it.

### 9.13 Recovery after a restart (`recover_interrupted`, deployer.py:5005)

- `_recover_instance(dep)` returns at once when `dep.instance` is None; for a member it writes the owner's fields through `owner_of` (§7.5).
- `activate` that was in `switch`, or whose `options.switch.changed`/`created`/`deleted` is non-empty: `traffic_state.unresolved = {…, message: "Slipway restarted during the switch"}`; audit `environment.unresolved`.
- `teardown`: status stays `deleting`; only its retry is accepted.
- A data owner job interrupted after `stop_slots`, `start_slots` included: phase 2's dirty and hold rules apply on the owner; the slots stay STOPPED and the hold text says so.
- A slot deploy interrupted during `start`: the owner is dirty; its `d` line stays in the owner's lock (§7.1), so the owner's next job waits for it as for any left lock.
- Any environment job `_recover_live` marks succeeded: the chain notice of §8.5.
- `remove_slot`, `publish`, `discard`: nothing beyond the failed status (`discard` changed only slot state and the owner's dirty mark, which it writes last, in its `settle` step).

### 9.14 Discard a failed idle-slot deploy (`POST /environments/{id}/discard {slot}`)

The way past a failed deploy to the idle slot when the active slot kept serving (D17).

**Refusals:** mode `slot`, or one app slot (`Roll back or retry instead: <blue> is <env>'s only slot`); the owner's dirty state doesn't name a deploy of `slot` (`<green> has no failed deploy to discard`); `slot` is the active one; no active slot (`Nothing is live to check the data with: roll back or retry`); the owner's hold; a job running; an unresolved switch.

**Steps** (kind `discard`, `traffic:switch` + `deployments:create`):
1. `check` (again at run time), then the owner's `revision` on the data server and the active slot's live `accepts` on it: 3 fails the step before anything stops (`<blue> (<sha7>) can't run the database at revision <r> that <green>'s deploy left: roll back to the backup from <time> instead`).
2. `stop_slot`: `docker compose stop` on green's projects (its half-started new release may be running against the shared database), STOPPED, `slot_state.stale = {reason: "Its deploy <d8> failed and was discarded", …}`.
3. `smoke`: the active slot's slot smoke test (§10.8) with the current database; a failure fails the job (`<blue> fails its check on the current data too (<codes>): roll back to the backup from <time> instead`) and leaves the dirty state as it was.
4. `settle`: `owner.data_dirty = NULL` in one transaction with the audit row `environment.discard`.

**Retry:** runs again. **Recorded:** the deployment, the audit row, `slot_state.stale`.

## 10. Traffic

### 10.1 An environment's routes

`traffic.routes(env, slot_instance, owner) -> list[Route]`:
- active-following: `slot_instance.app_state.routes` (what the target slot's release serves; slot role, so without `server.services`); before the slot deployed, `env.hostnames` filtered to `follows = active`;
- server-following: `owner.app_state.routes` of the data server (mode `server`);
- each `Route(hostname, service, container, follows, tls_mode = env.route_tls.get(hostname) or switchyard default_tls_mode, health)`.

A target is `{address: <slot or owner host>.upstream_address, port: the published host port for (service, container)}` (as `route_targets`, switchyard.py:220-245), or `problem` when the port isn't published, which is a blocker.

**What each operation may plan.** `mode = activate` plans every route, active-following ones for the target slot. `mode = sync` plans server-following routes for the data server and, only when the caller passes `include_active=True` (an in-place single-slot deploy, Publish names), active-following routes for the **recorded** active slot; with a switch unresolved it never includes them (I6). A data server deploy's sync passes `include_active=False`. `GET …/traffic/plan` with no `?slot` shows the sync plan; with `?slot` the activate plan.

### 10.2 The interface (`slipway/services/traffic.py`)

```python
@dataclass(frozen=True)
class Route: hostname: str; service: str; container: int; follows: str; tls_mode: str; health: str

@dataclass
class Change:
    hostname: str
    action: str              # create | update | delete | none
    external_id: str | None  # Switchyard host id, Cloudflare record id
    resource_id: uuid.UUID | None
    before: dict | None      # the object as read (for put-back)
    after: dict | None       # the body Slipway will write
    summary: str             # "api.uat.example.com → 10.0.0.12:8000 (was 10.0.0.11:8000)"

@dataclass
class Plan:
    backend: str
    changes: list[Change]
    blockers: list[str]      # any one: nothing is written
    notes: list[str]
    def to_json(self) -> dict

@dataclass
class SwitchContext:
    env: Environment; to_slot: Instance | None; owner: Instance | None
    routes: list[Route]; mode: str            # activate | sync | remove
    deployment_id: uuid.UUID | None; say: Log; connect: ConnectFactory

@dataclass
class Applied:
    changes: list[Change]        # what was written, in order, with the external ids
    apply_n: int | None          # Switchyard's last_applied.n after Slipway's apply, or None (no apply)

class TrafficBackend(Protocol):
    name: ClassVar[str]                                   # switchyard | do_lb (phase 4)
    async def configured(self, db) -> str | None          # why it can't be used, or None
    async def plan(self, ctx: SwitchContext) -> Plan      # reads only
    async def apply(self, ctx, plan: Plan) -> Applied     # writes; records as it goes
    async def verify(self, ctx, plan: Plan) -> None       # raises SwitchFailed; holds no lock
    async def put_back(self, ctx, plan: Plan, applied: Applied) -> PutBack  # never raises
    async def remove(self, ctx) -> Plan                   # teardown: plan of deletes, then applied

BACKENDS: dict[str, TrafficBackend] = {"switchyard": SwitchyardBackend()}
```

`traffic.switch(ctx) -> SwitchResult`, shared by every backend, is the whole of Activate's `switch` step (there is no separate `verify` step; the log marks the verify phase with a line `Checking the names through Switchyard`):
1. `plan = await backend.plan(ctx)`; logs every change and note; `mode = activate` with blockers → `SwitchRefused("…; Slipway changed nothing")`; `mode = sync` with blockers → logs them and returns a warning.
2. Saves the switch record on the deployment before any write: `options.switch = {backend, from_slot, to_slot, before: {hostname: before}, created: [], deleted: [], changed: [], applied: false, apply_n: null}` (own transaction). This record exists for recovery and Resolve; in-process the `Applied` object is used.
3. `applied = await backend.apply(ctx, plan)`; each write updates `options.switch.changed`/`created`/`deleted` in its own transaction, and the apply stores `apply_n`.
4. `await backend.verify(ctx, plan)` (mode `activate`; `sync` runs it with one round and warns).
5. On any exception **or cancellation** after step 2: the put-back runs as its own task, kept by a strong reference and awaited with `asyncio.shield` for up to 120 s; then `SwitchFailed` with `Traffic stays on <from>` / `Nothing was live before; Slipway removed the hosts it had made`, or, when `PutBack.failed`, `Slipway couldn't put <n> of <m> back: <names>. Check them in Switchyard, then use Resolve on the environment page`, which also sets `traffic_state.unresolved`.

**Locking.** `switchyard._lock` is taken for steps 1-3 together (plan, writes, apply: nobody else's sync can stage edits in between) and released before step 4. The put-back takes it again. Between the two, other instances' and environments' syncs run normally (they touch other hosts: one owner per host, §10.3). The put-back therefore (a) re-reads each host it changed and restores only hosts that still equal the body Slipway wrote (`after`), counting any other as not put back (unresolved); and (b) runs `_blocker` (switchyard.py:332) with Slipway's edit count kept by `_load_edits`/`_save_edits` against the **current** `last_applied.n`, which a sync applied in between has already reset, so another sync's apply is not mistaken for a foreign change. `apply_n` is logged with the put-back (`Switchyard applied #<apply_n> for the switch; putting back on #<n>`).

`traffic.plan_for(env, slot, db)` is the dry run (§10.7).

### 10.3 Switchyard backend: exact calls

All through `SwitchyardClient` (switchyard.py:126-190); plan and apply under `switchyard._lock`, verify outside it, put-back under it again (§10.2). The marker for an environment is `Managed by Slipway: environment <name> (<env id>). Domains, upstreams and TLS mode are set from Slipway when traffic moves.` `switchyard.Owner(kind, id, name)` generalises `_marker`/`_owned_by` (switchyard.py:248-253): `owned_by(host, owner)` is true when the notes hold `MARKER` and `str(owner.id)`, so instance-owned hosts keep matching as today. `describe_owner(host)` reads "instance X" or "environment Y" from the notes for conflict messages.

**plan** (reads only):
1. `GET /api/config/preview` → `_blocker(preview, own_edits)` (switchyard.py:332-342) as a blocker.
2. `GET /api/hosts` once → index by domain and id.
3. For each route, the recorded row `resources(env, switchyard, proxy_host, name = hostname)`:
   - row and a host with that id carrying this environment's marker → `update` when `_differs` (switchyard.py:276) against `_desired(host, target, owner)`, else `none`;
   - row whose host is gone or no longer carries the marker → the row is forgotten at apply (`resource.forget`), and the route is planned as if unrecorded;
   - no row: a host holding the domain → blocker `<hostname> is used by Switchyard host #<id>, which belongs to <describe_owner>`; a host whose `domains` list more than this name → blocker `Switchyard host #<id> serves <hostname> together with <others>; give it a host of its own`; none → `create`.
4. Rows for hostnames no longer routed → `delete` (re-checked at apply).
5. `before` is the host as read (minus `id`, `created_at`, `updated_at`).

**apply:**
1. For each change in hostname order:
   - `create`: `POST /api/hosts` with `_desired(None, target, owner)`; at once `resources.record(…, origin="created", provider_id=str(id), details={follows, upstream, tls_mode, url})`.
   - `update`: `GET /api/hosts/{id}` again (still carries the marker, else abort with a blocker text), then `PUT /api/hosts/{id}` with `_desired(host, target, owner)`; `resources.update_details`.
   - `delete`: `GET /api/hosts/{id}` (still ours), `DELETE /api/hosts/{id}`, `resources.forget`.
   Each counts as one of Slipway's own edits (`_load_edits`/`_save_edits`).
2. `GET /api/config/preview`: when `changes` exceeds Slipway's own edits since `last_applied.n`, or `drift`/`caddy_error` appeared → raise `SwitchFailed("Someone changed Switchyard during the switch")` (put-back follows, without an apply).
3. `POST /api/config/apply {"note": "Slipway: <env> → <slot>"}` (90 s) → `applied.version`; `options.switch.applied = true`.

**verify:** the public check (§10.8) for every route, outside `switchyard._lock`.

**put_back** (reverse order, each its own try):
- updated hosts: `PUT /api/hosts/{id}` with the recorded `before`;
- created hosts: `DELETE /api/hosts/{id}` and `resources.forget`;
- deleted hosts: `POST /api/hosts` with `before` (a new id) and `resources.record`;
- then, when the apply had happened or any edit was made, `POST /api/config/apply {"note": "Slipway: put back <env>"}`. If `_blocker` reports foreign changes at that point, the hosts are back but not applied: counted as a failure (`unresolved`).

**sync** (mode `sync`, after an in-place deploy, a data server deploy or in Publish names): the same plan and apply over the routes §10.1 allows a sync (never an active-following host to another slot), failures logged as warnings, put-back on a failed apply. After a data server deploy that created a host, the public check runs on the server-following names (12 rounds, warnings only).

**remove** (teardown): plan deletes for every row; apply deletes; the apply is skipped with a warning when blocked (deletes stay staged).

`_desired` keeps every field Slipway doesn't own (policies, headers, `enabled`) as today; the body's upstream is `target.address:target.port`, keeping the stored scheme and `skip_tls_verify`.

**Instances keep `sync`** (switchyard.py:283-307) unchanged; `deployer.has_routes` (deployer.py:4649) returns False for environment members (D22).

### 10.4 Cloudflare client

**Client** (`slipway/services/cloudflare.py`): base `https://api.cloudflare.com/client/v4`, `Authorization: Bearer <token>`, `User-Agent: Slipway`, timeout 30 s, `transport_factory` seam (tests). A 429 is retried once after `Retry-After` (at most 30 s). `CloudflareError(message, status_code, codes)`: Slipway's text plus Cloudflare's error codes and at most 200 characters of its message; the token never appears.

| Method | Call |
|---|---|
| `verify_token()` | `GET /user/tokens/verify` → `result.status == "active"` |
| `zone_id(zone)` | `GET /zones?name=<zone>&status=active` → exactly one, else `No active zone <zone> for this token` |
| `records(zone_id, name)` | `GET /zones/{zone_id}/dns_records?name=<name>&per_page=100` (exact name, every type) |
| `get_record(zone_id, id)` | `GET /zones/{zone_id}/dns_records/{id}`; 404 → None |
| `create_a(zone_id, name, content, proxied, comment)` | `POST /zones/{zone_id}/dns_records {type: "A", name, content, ttl: 1, proxied, comment}` |
| `update_a(zone_id, id, content, proxied, comment)` | `PATCH /zones/{zone_id}/dns_records/{id} {content, proxied, ttl: 1, comment}`; 404 → `RecordGone` |
| `delete_record(zone_id, id)` | `DELETE /zones/{zone_id}/dns_records/{id}`; 404 → False |

Comment: `Managed by Slipway: <env> (<env id hex[:12]>)` (under Cloudflare's 100-character limit).

**`plan_dns(wanted, records_by_name, wildcards, rows, env_id)`** is pure (tests). Per name, `wanted = {content, proxied}`:

| status | when | apply |
|---|---|---|
| `ok` | our row; the record is A with that content and proxied flag | none |
| `update` | our row; content or proxied differs | PATCH |
| `create` | no record of any type at the name, and no covering wildcard | POST, then record (origin `created`) |
| `covered` | no record at the name; `*.<parent>` is an A record with the wanted content and flag | none, not recorded |
| `claimable` | exactly one A record nobody records | blocker until claimed (§9.11) |
| `conflict` | outside the zone; a CNAME or an AAAA at the name; two or more A records; another environment's row holds the record id; our row's record was renamed, or is gone and a foreign A took the name | blocker |

Rows for names no longer wanted: origin `created` and the live record still A at that name with our comment → DELETE and forget; otherwise forget only. Claimed rows are only forgotten.

### 10.5 DNS publishing (fixed address)

`traffic.publish_dns(env, say)` (the `dns` step of `publish`, `activate` and the data server deploy): every route's record points at `env.traffic.dns.address or cloudflare.public_ip`, with `proxied = env.traffic.dns.proxied`. Plan with `plan_dns`; blockers stop the step before any write; then deletes of stale rows, updates, creates, each recorded at once (Sirdar's `ensure_dns`, sirdar-traffic §2). DNS never changes on a Switchyard switch. `traffic.remove_dns(env)` is the teardown half.

### 10.6 Unresolved switches

`traffic_state.unresolved` is set when a put-back couldn't finish (§10.2 step 5), an apply was refused after hosts changed, or recovery found an interrupted switch (§9.13). While it is set, refused with `Traffic of <env> may be split between its slots since <deployment d8> (<message>). Activate a slot, or use Resolve once Switchyard is right`: deploys to app slots, `remove_slot`, and restore, roll back and reset on the owner. Allowed: `activate` (either slot), Resolve, the data server deploy (its sync touches server-following hosts only), `publish` (without its active-following part), Back up now, snapshots without `stop_app`, delete. No sync of an active-following host runs while it is set (I6). A successful activate or Resolve clears it.

### 10.7 Dry runs

`GET /environments/{id}/traffic/plan?slot=<slot>` (environments:read) returns `{switch: Plan | null, dns: Plan | null, routes: [...]}` with no write: the Activate dialog, the Traffic card and the flow's Traffic step use it. Every switch and publish logs its plan before its first write. Without `?slot` it returns the sync plan (§10.1: server-following routes, and active-following ones for the recorded active slot); with `?slot` the activate plan for that slot. Switchyard or Cloudflare errors answer 502 with the client's text.

### 10.8 Smoke test and public check

**Slot smoke test** (on the slot's host, one SSH command per name):

```
curl -sS -o /dev/null -w '%{http_code}' --max-time 10 -H 'Host: <hostname>' -H 'X-Forwarded-Proto: https' \
  'http://<bind>:<host port><health>'
```

`<bind>` is the published port's `host_ip` when it is a specific address, else `127.0.0.1`. Every value is quoted with `q()`. Without `curl` on the host, `wget -q -S -O /dev/null --header … 2>&1 | awk '/^  HTTP/{c=$2} END{print c}'`; without either, the step fails `Neither curl nor wget is on <host>; install one`. 200-399 passes; 5 tries per failing name, 10 s apart; redirects are not followed. Routes that follow the data server are not part of a slot's smoke test.

**Public check** (from the Slipway server, `traffic.public_check`): for each route, `GET https://<traffic_address><health>` with `Host: <hostname>` and `extensions={"sni_hostname": hostname}`, a fresh `httpx.AsyncClient` per name (no pooled connections), timeout 10 s, certificate verified against the hostname. `tls_mode = internal` → `verify=False`, logged; `off` → `http://`. 200-399 passes; 6 rounds 10 s apart, only failures retried; 12 rounds when the switch created a host (Caddy is getting a certificate). No `traffic_address` set: skipped, `warning` note `Set Switchyard's traffic address in Settings → Integrations so Slipway can check the names through it`. `traffic.transport_factory` is the test seam.

### 10.9 Phase 4's load-balancer backend (contract fixed now)

`do_lb` implements `TrafficBackend`: `plan` reads the recorded `load_balancer` resource and its `droplet_ids`; `apply` adds the new slot's droplet, waits for the slot's own `/healthz` over SSH (`ctx.connect`) and the LB's settle time, runs the public check through the LB address, then sets only the new droplet and proves the switch by re-reading (sirdar-traffic §6); `put_back` PUTs the previous `droplet_ids`. DNS stays a fixed-address publish at the LB's IP. Nothing in `traffic.switch`, the Activate flow, `options.switch` or `traffic_state` changes for it.

### 10.10 Settings and tokens

- Cloudflare (`PUT /settings/cloudflare {zone, public_ip, proxied, token?, clear?}`, `settings:write`): the token is required the first time and write-only after (`has_token`, `token_hint` = its last 4 characters); saving looks the zone up (`zone_id`) and verifies the token (422 with the client's text). `POST /settings/cloudflare/test`: token active, zone found, records readable (`GET /zones/{id}/dns_records?per_page=1`) → `Connected: zone <zone>; the token is active and can read its records. Slipway can't check that it may edit them without changing one.`
- Switchyard (`PUT /settings/switchyard`) gains `traffic_address` (`host[:port]`, validated as a hostname or IP).
- Both secrets are `AppSetting.secret` (EncryptedText) and covered by `rotate-encryption-key`. Clearing Cloudflare while an environment has `traffic.dns` is refused: `Environments <names> publish DNS records through Cloudflare; turn that off on them first`.

### 12.3 Deploy flow (`/environments/new`, `need(ctx, Perm.ENVIRONMENTS_WRITE)`)

One page, seven `<section data-step>`s, a numbered stepper (`aria-current` on the current step, earlier ones done), a live region `Step N of 7: <name>`, and a footer **Start over** (`confirm()`: `Start over? Every choice on this page is cleared.`), **Back**, **Next** / **Deploy**. **Next** runs the step's client checks, then `POST /environments?check=true` with what is filled so far; a `field` in the answer marks that field and moves to its step (the `FIELD_STEP` map in slipway.js). The steps:

1. **Environment**: Name (`^[a-z][a-z0-9-]{0,24}[a-z0-9]$`, `Up to 26 characters: the slots are <name>-blue, <name>-green and <name>-data`), Repository (synced repositories whose default branch has slipway.yml), Branch (default the repository's), Advanced: manifest path. The manifest is fetched with `GET /repositories/{id}/manifest?branch&path` (as the instance form, slipway.js:1111).
2. **Servers**: `( ) Single slot` / `( ) Blue/Green`; Single adds `[ ] Keep the data on a server of its own` (mode `server`). Blue/Green is disabled, with the reason, unless the manifest has the `bluegreen` capability. Hints: `One slot: each deploy updates it in place.` / `Each deploy goes to the idle slot; Activate moves the traffic to it. A third host holds the data both slots use.`
3. **Hosts**: selects of Hosts for Blue, Green and Data server (unpinned hosts disabled `Check it first`; for mode `server`, hosts whose LAN or proxy address isn't an IP disabled `Its address must be an IP for the data server to let it in`; the data server's select disables the app slots' hosts, `The data server needs a host of its own`); a warning when both app slots share a host; a link to add a host.
4. **Settings**: the manifest's settings, optional services and environment variables, built like the instance form's app section (`wireAppForm`).
5. **Traffic**: read-only table Public name · Through (`Switchyard (<traffic address>)`) · To (`Blue on <host>` / `The data server on <host>`) · TLS (select, default Switchyard's). Switch: `( ) Switchyard` / `( ) None` (single only). DNS: `[ ] Publish DNS records in Cloudflare` (enabled when set up), address (default the integration's public IP), `[ ] Proxied`. Blue/Green: `[ ] Activate automatically when the smoke test passes`. The dry run (`traffic/plan` isn't available before create; the check answer's `plan.traffic` fills the table).
6. **Data**: `( ) Start empty` (first-admin fields from the manifest, password or invite, as P2 §15.4) / `( ) From a snapshot` (ready snapshots of the same app; permission notes); Backups to keep.
7. **Review & Deploy**: a definition list of every choice; `Secrets: generated by Slipway and never shown`; footnote `Deploy creates the environment and starts its first deployment, then opens it.` **Deploy** = `POST /environments` then `POST /environments/{id}/deploy`, then `location.assign("/environments/<id>")`. A lost answer or a 5xx on the create marks the name unsure; a later `already exists` then shows `It may have been created already: open it`. A create that succeeded with a start that failed locks the page on Review with `Created <name>, but its first deployment didn't start: <reason>. Open the environment` and **Deploy** retries only the start.

`/environments/{id}/edit` reuses steps 4-6's fields for PATCH (read-only without environments:write; `Saved. The next deploy to each slot uses these settings.`).

## 13. Concurrency, limits, timeouts

- One job per environment, except Activate beside a read-only data job (§8.2); one Switchyard write batch at a time (global lock, never held across a check or a wait).
- Slot smoke: 5 tries × 10 s per name, `curl --max-time 10`, the SSH command's timeout 60 s. Database probe: `connect_timeout=10`, the SSH command's timeout 120 s (an image pull). Public check: 6 rounds × 10 s (12 when a host was created), 10 s per request. Switchyard calls 30 s, apply 90 s. Put-back: shielded, 120 s. Cloudflare calls 30 s, one 429 retry ≤ 30 s.
- At most 50 routes per environment (`Too many public names (<n>); Slipway manages at most 50 per environment`), 2 app slots, 1 data server.
- `env_steps_for` timeouts: `check` 2 min, `switch` 20 min (plan, apply, verify phase and put-back), `dns` 10 min, `stop_slot` 10 min, `settle` 1 min, `seed` the manifest's, `unroute`/`undns` 10 min, `slot`/`slots`/`data_server` 30 min each.

## 14. Room for phases 4-6

- **Phase 4 (DigitalOcean).** `data_mode = managed`: the data endpoints come from `resources` (`database`, `bucket`, `spaces_key` with `credentials`) instead of a data server, through the same `data.attach` and `{data.*}` values. The data owner is still a `slot = data` instance (D3) that runs no containers: its data commands run, at job time, through a member session on the active slot's host (or the Slipway server), and its Backup, FirstAdmin and dirty-state rows never move. Backups move to the Slipway server (`Backup.location`). The `postgres` need's `database`, `user` and `password` (one named secret) are what phase 4 creates the role and database from (Sirdar's `do_provision.py:945-961`); `tls: require` with the cluster's `ca_b64`. Droplets are `Host` rows with `provider = digitalocean`, `provider_id`, a pre-pinned `host_key` and `owner_environment_id`; teardown destroys owned hosts after `slots`. `do_lb` is a `TrafficBackend` (§10.9); production and the delete phrase are environment flags added then.
- **Phase 5 (Proxmox, ESXi).** VMs are hosts with `provider = proxmox | esxi` and a `vm` resource. They don't exist when the environment is created, but slot instances need a `host_id` (NOT NULL, RESTRICT): create makes **planned** host rows (`provider` set, `hostname` the address to be, `host_key` NULL, so unpinned) that the slots point at, and a `prepare` step before `resolve` makes or resizes the VM, then pins its key. Every phase 3 refusal of an unpinned host stays, except in a job whose first step is `prepare`. VM snapshots get their own table.
- **Phase 6 (retire Sirdar).** Nothing to import; the environments pages replace Sirdar's.

## 18. Open questions, with the default chosen

1. **Data server firewall.** Sirdar installed `DOCKER-USER` rules so only the app hosts reach Postgres and the object store. Default: **not built** (D19); access is the app's own `pg_hba` (`{server.clients}`) and the S3 key; the environment page's Data card says the data server's ports are reachable from the whole LAN, and docs/environments.md shows the rules to add by hand and `STACK_BIND_IP`. A `data.server.firewall` step for hosts with passwordless sudo can come later.
2. **Typed name for Activate.** Default: **no** (Activate is reversible by switching back). Phase 4's production flag adds it there.
3. **Delete removes the data volumes.** Default: **no**; volumes and backups stay on the data host (P2 D18 semantics), and the dialog says how to remove them.
4. **Developers may switch traffic.** Default: **yes**, `traffic:switch` is in the developer role, as in Sirdar where everyone who deploys may activate; maintainers keep creating, configuring and deleting.
5. **What the data server builds.** Default: the manifest's `build` (for ServerSherpa every image), because `export-objects` and `import-objects` on the data server need the api image. A lighter `data.server.commands.build` can be declared later.
6. **AAAA records.** Default: **A records only**; an AAAA at a managed name is a conflict.
7. **DNS switching backend** (`switch = cloudflare`). Default: **not built** (D14): it can't be checked through the real path or put back for clients that cached the old answer, and ServerSherpa's LAN slots don't terminate TLS. `TrafficBackend` keeps room for it.
8. **Two roles on one host.** Default: two app slots on one host **allowed with a warning**; the data server on an app slot's host **refused** (D18: `pg_hba` can't let a same-host container in by host address).
9. **Public check reachability.** Default: from the Slipway server to Switchyard's `traffic_address`; skipped with a warning when it isn't set.
10. **Roll back after a successful activation.** Default: **not offered**; Switch back, or restore the pre-deploy backup by hand (D17).
11. **Two slots without expand/contract.** Default: **refused** (D7) rather than a cutover mode that stops the live slot.
12. **Extra hostnames on an environment** (beyond the manifest's). Default: **not in phase 3**; only per-name TLS mode overrides (`route_tls`).
13. **Data server port moves.** Default: refused before `start` (§9.7), since the slots' `.env`s name the old ports; Slipway keeps ports stable through `port_overrides`.
14. **Settling a failed idle-slot deploy.** Default: **Discard** first (nothing restored; the active slot is checked on the current data), **Roll back** second with `data:reset` and a lost-writes warning (D17).
15. **The lag check after a switch back.** Default: **refuse with an explicit override** (`acknowledge_schema`) rather than always refuse, so the fix-and-redeploy loop after a switch back works (D7, §7.6).
16. **Activate beside other jobs.** Default: only beside the owner's Back up now and a snapshot without `stop_app` (D8); never beside a deploy, a restore kind, a stopping snapshot or teardown.
17. **When a new environment seeds starter content.** Default: in its **first Activate**, after the switch (D24), because the content uploads through the environment's public names.
18. **Environment name length.** Default: **2-26 characters** (§2), so `<env>-green` fits ServerSherpa's 32-character `STACK_ENV`. Apps with a tighter limit fail in their own commands; Slipway doesn't learn per-app limits.
19. **Data server identity values.** Default: the server's `.env` keeps the identity secrets **blank** (D18); Slipway records the environment's values from `AppPlan.identity`. The alternative, writing every secret on the data server, would have fixed points 1 and 2 of the review with no ss-stack change, but puts the JWT secret, pepper and TOTP key on the host that holds the data they protect.
